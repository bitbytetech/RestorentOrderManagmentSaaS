## 3. Multi-Tenant Architecture & Domain Scoping

### 3.1 Data Scoping Strategy
The platform utilizes **Row-Level Shared Database Multi-Tenancy**. Every business entity belongs to an `Organization` (`tenant_id`).


```

[ Organization / Tenant ] (e.g., Royal Cafe Group)
├── Tenant Admin (Owner)
├── Master Menu (Categories, Items, Variants)
├── Subscription Tier (e.g., Growth Plan)
│
├── [ Outlet 1: Hazratganj ]
│     ├── Outlet Manager, Cashier, Kitchen Staff
│     ├── Tables (T1, T2, T3...)
│     ├── Price Overrides & Item Availability Flags
│     └── Orders (QR + Counter)
│
└── [ Outlet 2: Gomti Nagar ]
├── Tables (GT1, GT2...)
├── Price Overrides & Item Availability Flags
└── Orders (QR + Counter)

```

### 3.2 Tenant Isolation Safeguards
1. **Django Model Manager Scoping:** All database models (Menu, Order, Table) inherit from a custom `TenantAwareModel` class that enforces `organization_id` on querysets.
2. **Middleware Context:** A custom `TenantMiddleware` extracts the authenticated user's `organization_id` or resolved outlet slug from the URL request path and injects it into request thread locals.
3. **Cross-Tenant Guard:** API endpoints validate that requested `outlet_id` belongs strictly to the user's logged-in `organization_id`.

## 5. Detailed Functional Specifications

### 5.1 Onboarding & Organization Setup
- **Registration Flow:** Owner signs up with Brand Name, Owner Name, Mobile Number (OTP Verified), Email, and Password.
- **Mandatory First Outlet:** Registration wizard forces creation of Outlet #1 (Name, Address, City, Contact, Opening Hours) before accessing the dashboard.
- **Multi-Outlet Expansion:** Owners can add extra outlets up to the maximum permitted by their subscription tier.

---

### 5.2 Menu, Variant & Category Management

#### Hybrid Structure: Categories vs. Tags
- **Categories (Primary Structural Hierarchy):** Single selection per item (e.g., *South Indian, Chinese, Continental, Desserts, Beverages, Alcoholic Drinks*). Drives top tab navigation on mobile web.
- **Tags (Multi-Select Filters):** Flexible attributes (e.g., *Veg, Non-Veg, Egg, Chef Special, Spicy, Jain, Bestseller, Sugar-Free*). Enables instant filtering without altering category views.

#### Advanced Variant Engine
Mathematical fraction-based auto-pricing fails in real F&B operations. The system implements an **Explicit Variant Architecture**:
1. **Simple Flat Items:** e.g., Mineral Water ₹20 (Single Default Variant).
2. **Sized Portion Variants:** Full Noodles ₹120, Half Noodles ₹75 (Non-proportional custom pricing).
3. **Weight & Unit Variants:** Kaju Katli (Unit: Gram/Kg) → 100g = ₹120, 250g = ₹300, 1000g = ₹1150.
4. **Supported Units:** `full`, `half`, `quarter`, `piece`, `plate`, `bowl`, `glass`, `gram`, `kilogram`, `liter`, `ml`.

#### Outlet Override & Sync Architecture
- **Master Item Repository:** Items created at Organization level.
- **Outlet Overrides (`outlet_menu_override`):**
  - **Availability Toggle:** Mark item/variant as "In Stock" or "Sold Out" per outlet.
  - **Price Override:** Charge ₹150 for Full Noodles in Airport Outlet vs ₹120 in High Street Outlet.
- **Outlet Cloning Wizard:** Allows copying full menu hierarchy, pricing rules, and tags from Outlet A to Outlet B with one click.

---

### 5.3 QR Code & Table Management System

#### Dynamic QR Structure
- **Table QR URL Format:** `https://<domain>/o/<outlet_slug>/t/<table_code>`
- **Takeaway QR URL Format:** `https://<domain>/o/<outlet_slug>/takeaway`

#### Table Policy Controls
- Restaurant Owner / Outlet Manager sets the **Table Editing Rule**:
  - `STRICT_ENFORCED`: Customer *cannot* change the table number detected from the scanned QR code.
  - `CUSTOMER_EDITABLE`: Customer can edit or re-select their table number from a dropdown (useful if seating changes or for broad area/patio ordering).

---

### 5.4 Dual Ordering Engines (QR & Counter POS)

#### Flow A: Customer QR Ordering (Dine-In & Takeaway)
1. **Scan & Resolve:** Scans QR code → Web page resolves `outlet_id` and `table_code` (if present).
2. **Mobile Auth:** Customer enters 10-digit mobile number (cached in browser session storage).
3. **Menu Exploration:** Filters by Veg/Non-Veg tags or browses categories with sticky header search.
4. **Variant Selection:** Selects portion/weight variant (e.g., Half, 250g) and adds notes (e.g., "Extra spicy").
5. **Cart & Submit:** Order payload submitted via AJAX/Alpine fetch. State set to `PLACED`.
6. **Order Tracking Page:** Customer views real-time status bar (`Placed` → `Preparing` → `Ready` → `Delivered`).

#### Flow B: Counter / Cashier POS Ordering (Walk-In / Phone / Takeaway)
1. **POS Dashboard:** Optimized desktop/tablet interface with keyboard shortcuts and quick category grid.
2. **Order Type Selection:** Cashier toggles `Dine-In` (selects available table) or `Takeaway` / `Counter Walk-in`.
3. **Customer Mobile Capture:** Cashier asks and enters customer's mobile number (autocompletes past customer profile).
4. **Fast Cart Builder:** Instant item search, variant tap, custom item discount input.
5. **Payment Collection:**
   - Cash / UPI / Card / Pay Later toggle.
   - Cashier clicks **"Place & Print KOT"**.
6. **Instant Status:** Order bypasses initial verification and directly enters `CONFIRMED` or `PREPARING`.

### 5.5 Order Lifecycle & State Machine

Order state transition rules enforce operational consistency:

- `PLACED`: Customer submitted QR order. Awaiting automated or cashier confirmation.
- `CONFIRMED`: Order accepted by counter/kitchen. KOT generated.
- `PREPARING`: Food is actively being prepared in the kitchen.
- `READY`: Dishes prepared; ready for table service or counter takeaway pickup.
- `DELIVERED`: Order fulfilled and served to table/customer.
- `CANCELLED`: Cancelled by cashier/manager or rejected due to out-of-stock items. Requires cancellation reason logging.

---

### 6. Analytics & Pre-Aggregated Reporting Engine

To prevent database bottlenecking during peak operational hours, financial and item sales aggregations are performed via Celery background tasks into pre-aggregated summary tables.

#### Reporting Views
1. **Executive Dashboard KPIs:** Real-time Today's Revenue, Order Volume, Active Tables, Average Order Value (AOV), Pending Orders.
2. **Sales Analytics:** Filters for Daily, Weekly, Monthly, Yearly, and Custom Date Ranges. Breakdowns by:
   - Total Business (All Outlets)
   - Outlet vs Outlet Comparison
   - Category Breakdown (e.g., Beverage % vs Food %)
3. **Item Performance Matrices:**
   - **Top Sellers:** Ranked by total sales volume (quantity) and revenue generated (Overall & Store-specific).
   - **Low Sellers:** Bottom 10 items to identify menu clutter or wasted stock.
   - **Variant Spread:** Sales volume ratio of Full vs Half portions.

## 10. Non-Functional Requirements & Security Specifications

### 10.1 Performance SLAs

* **Menu Load Time:** Sub-100ms response time for customer QR scanning via Redis cached JSON payload.
* **POS Order Placement:** Sub-200ms processing latency for counter cashier order submission.
* **Reporting Queries:** Dashboard pages must load in < 1 second using pre-aggregated analytics tables.

### 10.2 Security Controls

* **Password Hashing:** Django standard Argon2 / PBKDF2 with HMAC-SHA256.
* **Data Isolation:** All database queries filtered strictly by `organization_id` context.
* **Input Sanitization:** Protect against SQL injection and XSS in item descriptions and custom instructions.
* **Rate Limiting:** Redis-backed rate limiter on customer order submission endpoints (Max 5 orders per mobile number per 10 minutes) to prevent spam.
